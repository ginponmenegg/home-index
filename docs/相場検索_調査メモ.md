# 相場検索（不動産情報ライブラリ XIT001）調査メモ

2026-09-10 調査。**この時点では作らないと決めた。** Renderの容量を増やせる
段階になったら、ここから再開する。

実際にAPIを叩いて測った数字なので、次に検討するときは推測から始めなくてよい。
ただし数字は取得時点のもの。再開するときは1回だけ叩き直して確かめること。

---

## 作らないと決めた理由

いまのRender無料プラン（メモリ512MB）では、取引データのキャッシュが載らない。
「どの市区町村でも選べる」機能なので、キャッシュの設計が本体になる。
容量を増やせるまで、設計だけ寝かせる。

## 実測した数字（2026-09-10 / 船橋市 12204 / 2024年）

XIT001 に `year` と `city` だけを渡した結果。

| | |
|---|---|
| 件数 | 2,320件 |
| 転送量 | gzip 66KB |
| JSON | 2.07MB |
| **Pythonオブジェクト（Transaction）** | **5.1MB** |
| `raw` を捨てた場合 | 1.6MB |
| 応答時間 | 0.93秒 |

### 四半期は指定しなくてよい

APIマニュアルには `quarter` が**必須**と書かれているが、`year` だけで
4四半期すべて返る。

    2024年第1四半期 589 / 第2 557 / 第3 570 / 第4 604

つまり **1リクエスト＝1市区町村×1年（全4四半期）**。現行の
`src/reinfolib.py` の呼び方は正しい。マニュアルの記載に合わせて `quarter` を
足す必要はない（足すとリクエストが4倍になる）。

### 2種類のデータが混ざって返る

`priceClassification` を指定しないと、両方が混ざる。

| PriceCategory | 件数 | 中身 |
|---|---|---|
| 不動産取引価格情報 | 1,371 | 登記をもとにした当事者アンケート。2005年〜 |
| 成約価格情報 | 949 | REINSの成約。2021年〜 |

現行コードは指定していないので混ざったまま使っている。どちらも悉皆ではない。
相場として出すなら、どちらを使ったか画面に書く必要がある。

### 町名あたりの厚み（1年分）

| 種別 | 年間件数 | 町名数 | 中央値 | 3件以上ある町名 |
|---|---|---|---|---|
| 中古マンション等 | 1,050 | 63 | 11件 | 53地区 |
| 宅地(土地と建物) | 962 | 75 | 10件 | 61地区 |

**船橋市（人口64万）でこの厚み。** 小さい市町村では大半の町名が1〜2件になる。
件数を必ず画面に出し、閾値未満は数字を出さない設計が要る。

### 使えるパラメータ

- `year`（必須・取引価格は2005〜／成約価格は2021〜）
- `city`（5桁）／ `area`（都道府県2桁）／ `station`（駅コード6桁）── いずれか1つ以上
- `priceClassification`（01=取引価格のみ／02=成約価格のみ／未指定=両方）

**`station` が使える。** 「駅の相場」は町名より検索需要が大きいはずで、
再開するときの第一候補。駅コードの一覧をどこから取るかは未調査。

## 再開するときに最初に解く問題

### 1. キャッシュ

`src/reinfolib.py` の `_TXN_CACHE` は上限が**2000エントリ**。1エントリ5.1MBなので
埋まると約10GB。件数ではなく**概算バイト数**で持つか、LRUにする。

`Transaction.raw` は**どこからも読まれていない**（`.raw` の参照はすべて
`ScoreCategory.raw` という別物のfloat）。捨てるだけで 5.1MB → 1.6MB。
ただし捨てると `PricePerUnit` `UnitPrice` `Use` `Purpose` `Direction`
`Frontage` `CoverageRatio` `FloorAreaRatio` `Renovation` `Remarks`
`DistrictCode` に触れなくなる。相場検索で使うものは名前付きフィールドに
昇格させてから捨てること。

Neon（PostgreSQL）に集計結果を置く案は、**そのままでは採れない**。Neonの無料枠は
「起動していた時間」で課金され5分アイドルで自動停止する。検索のたびに起こすと
月100 CU時間を超える（`src/db.py` の冒頭に同じ理由が書いてある）。
集計を1日1回まとめて書き、読みは静的ファイル、という形なら成立するかもしれない。

### 2. APIの叩き方

マニュアルの記載：

> リクエスト数の明確な上限はありませんが、APIを実行する際は、間隔を空けて
> リクエストするなど、連続して実行しないようお願いいたします。

公開検索は 1検索＝最大10リクエスト（年数分）を誰でも何度でも撃てる。
`RATE_LIMIT_PER_DAY=40`（IP単位）では足りない。キャッシュが先。

### 3. 数字が二重になる

診断の「価格評価」は**類似度で加重した近傍6件から、その物件の推定価格**を出す。
相場検索は**その町名の中央値**を出す。同じ町名で違う数字が出るのが当たり前で、
説明がないと矛盾に見える。

宅建士がやっているサービスで「数字が合わない」は、いちばん失ってはいけない。
役割を分けて設計すること（例：相場検索は㎡単価の分布だけを出し、物件価格は
出さない）。

### 4. URL設計（SEO）

- `/souba/12204/前原西` のような静的URLならサイトマップに載せられる。
  市区町村1,700×種別で、いまの記事12本とは桁違いの面積になる。
- `?city=...&type=...` のクエリ検索は noindex にしないと薄いページが無限に増える。

面積が大きいぶん、中身が薄いと逆効果。粒度と一緒に決める。

## 派生してわかった、相場検索とは別の宿題

### A. 非商用条件つきのデータを表示している（未処理・要判断）

不動産情報ライブラリは**データごと・自治体ごと**に商用利用の可否が分かれる。
取引価格情報・成約価格情報は商用○だが、以下は「**一部非商用**」。

| API | 内容 | 非商用の対象（要確認） |
|---|---|---|
| XKT028 | 津波浸水想定 | 宮城・千葉・三重・京都・島根・長崎・大分 |
| XKT029 | 土砂災害警戒区域 | 京都・神奈川・和歌山・鳥取・広島・長崎 |
| XKT021/022 | 地すべり／急傾斜地 | 岩手・宮城・福島・岐阜・三重・岡山・福岡・長崎・大分 ほか |
| XKT016 | 災害危険区域 | 複数市町村 |
| XKT004/005 | 小学校区・中学校区 | 複数都県の市町村 |

いずれも `src/enrichment.py` で取得して画面に出している。PROが有料になった以上、
これらの県で該当レイヤを出すのは条件に触れる可能性がある。
見本物件（千葉県船橋市）は津波が非商用対象の県。

**県名の正確な一覧は https://www.reinfolib.mlit.go.jp/help/contents/ の
「非商用となっている範囲はこちらを参照ください」のリンク先で確認すること。**
上の表はページの要約から拾ったもので、一次情報ではない。

対処自体は重くない。`enrichment.py` は取得できないものを unknown で返す作りが
あるので、対象の都道府県だけ取りに行かない分岐を足せばよい。

### B. マンション診断が1市区町村あたり約51MBを積む（未処理）

`config.json` の `mansion_trade_years` が **10**。1市区町村の初回診断で
10リクエスト＝約51MBがプロセス内キャッシュに載る。戸建は3年で約15MB。

相場検索を作らなくても、**新しい市区町村のマンション診断が10件続けば
512MBに届く**。いまはアクセスが少ないので表面化していないだけ。

`Transaction.raw` を捨てるだけで 51MB → 16MB になる。これは相場検索とは
独立してやる価値がある。
