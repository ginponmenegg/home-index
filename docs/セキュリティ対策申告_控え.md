# セキュリティ対策措置状況申告書（控え）

割賦販売法にもとづく申告。クレジット取引セキュリティ対策協議会の
実行計画に沿って、オンラインでカード決済を行う事業者が提出する。
**毎年の更新がある**ので、次に聞かれたときのためにここへ置いておく。

2026年9月5日、Stripeの本番アカウント有効化の過程で提出。このとき
「その他の対策」だけが選択され、説明の入力欄が表示されないまま送信
された。再編集できなかったため、実態をここに残す。追加で照会が来たら、
下の内容をそのまま送ればよい。

---

## 実施している対策

### カード情報の非保持化

**カード情報は当サービスのサーバーを一切通過・保持しない。**
決済は Stripe Checkout、カード情報の変更は Stripe Customer Portal を
使用し、いずれも Stripe がホストする画面で完結する。

実行計画の中核がこれで、いちばん強い答えでもある。設計時に意図して
こうした（`src/billing.py` の冒頭を参照）。

> **自前のカード入力欄を作ると、この申告が事実でなくなる。**
> 決済まわりを触るときは必ずここに戻ること。

### ユーザー登録時の本人性の確認

登録メールアドレス宛に送信したリンクを開かない限り、登録もログインも
完了しない。当該アドレスの受信権を検証している。

### ログイン試行回数の制限とスロットリング

- 同一メールアドレスへのログインリンク発行：**1時間あたり5回まで**
- サービス全体：**1日80回まで**

（`src/accounts.py` の `PER_EMAIL_PER_HOUR` / `PER_DAY_TOTAL`）

### パスワードを保管しない

ログインは使い捨てリンクのみ。**有効30分・1回限り。**
リンクの文字列は保存せず SHA-256 のハッシュのみを保持するため、
データベースが漏えいしてもログインリンクは復元できない。
検証に失敗した場合は理由を返さず、一律のメッセージを表示する
（総当たりの手がかりを与えないため）。

### そのほか

| 項目 | 状況 |
|---|---|
| 通信の暗号化 | 全ページ HTTPS |
| 不正利用対策 | Stripe Radar（Lite） |
| 診断のレート制限 | IPあたり1日40回（`RATE_LIMIT_PER_DAY`） |

## 実施していないこと（聞かれたら「なし」と答える）

- 二段階認証・多要素認証（メールリンクは1要素）
- 不審IPの判定によるアクセス制限（ログインには掛けていない）
- 行動分析
- デバイスフィンガープリント

**ここを実態より大きく書かないこと。** 申告書に書いた対策は、
やっている前提で見られる。
